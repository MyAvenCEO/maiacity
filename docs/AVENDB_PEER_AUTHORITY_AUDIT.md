# avenDB peer authority audit — task 31 partial evidence

23 October 2026. Read-only source audit of the integration branch. This is a bounded audit, not completion of task 31 or physical server-absence acceptance (task 32). No production identities, stores, permissions or network state were changed. Source paths are repository-relative; line numbers are navigation hints.

## Conclusion

The inspected synchronization, file-provider selection and local reopen paths do not grant data authority merely because a node is a server. Authority remains signed vault membership/grants, authenticated peer identity and ordinary record/file validation. The application does retain central service and bootstrap dependencies, and a migration safety predicate selects governed aven/device peers. Those availability dependencies should be tested and generalized carefully; deleting their safety gates would not establish P2P correctness.

A separate existing bootstrap master-recovery owner is real authority, but is not authority granted to the online server role. Its ownership policy must be reported explicitly rather than conflated with server neutrality.

## Existing coverage and limits

Evidence already recorded in the upgrade ledger (this audit did not rerun tests):

- `live_tests.rs::a_live_edit_reaches_an_authorized_peer_while_its_background_pages_are_stalled_without_server`: authorized decrypted live delivery and subsequent convergence between ordinary direct peers.
- `a_live_hint_does_not_authorize_a_private_entry` and `witness_hints_preserve_permission_budget_and_duplicate_suppression`: private entry/identity fences and bounded hints; part of the recorded three passing live tests.
- `files_fetch_tests.rs`: recorded stalled-provider fallback, cancellation, advancing-progress behavior and verified-range resume. These are file availability scenarios, not proof every server-malicious case is covered.
- `moving_tests.rs::retirement_probe_covers_every_live_peer_subset_and_stays_fail_closed`, `an_eligible_local_move_still_requires_freshness_while_offline`, and no-work/next-key discovery tests: recorded migration-preflight checks. Their purpose is preserving current safety gates, not proving their topology independence.
- `upgrade_rehearsal.rs`: exact identity, edit/key set and visible record preservation on a marked offline disposable copy. This is not physical device acceptance.

Source-present supplemental coverage to inspect/run before relying on it: `avendb/crates/avendb-net/tests/packet_transport.rs::authenticated_sync_over_fragmented_carrier_without_ip_or_relay`, and `tests/server.rs` founding/claim, server-key-move and ordinary access-request scenarios. Merely finding a test is not a current passing result.

## Next bounded tasks

1. Specify retirement coverage in Lean in terms of authenticated authorized history witnesses, including what remains unknown when peers are absent. Map current gate and reject any relaxation that could cut unseen valid history.
2. Add topology substitution regressions: same authorized operations with server vs ordinary peer, server absent while another peer remains, and governed agent replacing governed server. Assert equal authorization outcomes and explain intentional admission-service differences.
3. Add adversarial peer scenarios: forged/missing frontiers, wrong identity/next key, invalid signed pages, unauthorized file claims and stale grants. These must preserve local state and refuse unverified authority regardless of peer role.
4. Exercise browser/native transport with the server data process stopped while relay remains, then relay stopped separately. Report reachability honestly; no offline delivery guarantee.
5. Audit product bootstrap alternatives and current recovery-owner policy explicitly. Separate enrollment availability improvements from synchronization/data-authority changes.
6. Finish physical Mac/iPhone/iPad no-reset tests and production backup recovery; preserve identity and exact canonical history. Only then close the corresponding acceptance rows.

No production change is proposed solely from terminology. The present audit establishes concrete call sites and remaining tests; it does not establish that every server role or every service dependency in the repository has been audited.
