# avenDB task 18: app/view/query demand inventory

Status: partial task 18 handoff; source audit only. Audited 2026-10-23 at `918c07fe` in the `codex/avendb-reliability` worktree. References below are repository-relative and refer to that snapshot. No production code changed, no account/store was opened, and no tests or builds were run for this audit. Existing tests were inspected, not revalidated.

## What exists already

The application already has route manifests, learned entry demand, renewable node leases, reusable read windows, and Library viewport demand. Task 18 is therefore an integration and semantics task, not a replacement of an absent system. The main gaps are incomplete consumer coverage, route context that is narrower than the UI's actual context, incomplete dependency reporting, cancellation that stops publication or subsequent work but not an active read, and query results with no authenticated completeness contract.

## Completeness and dependency boundaries

The current query engine iterates held `lab.entries(me)`, applies current policy, schema/lens interpretation, filters and sorting, then offset/limit (`avendb/crates/avendb/src/engine.rs:832`). Its response at `:885` contains `rows`, `count`, `plan` and `depth`. It contains no exact history revision, query fingerprint, authenticated matching-set coverage, missing dependency list, or global completion assertion. `cut` records depth truncation; it is not sync completeness. A posts response's `more` similarly describes the local page source.

Consequently, an empty local query can identify no further matching IDs unless an explicit positive entry filter, manifest, known index, or authenticated remote discovery provides them. Adding result-row leases cannot solve this circular case. Schema, lens and group entries also need a principled dependency report when they affect interpretation or selection; arbitrary traversal of a record cannot establish that report is complete.

Existing safeguards should remain visible:

- `src/lib/avendb/sync.svelte.js:25` explicitly describes sync percentage as relative coverage of announced peer logs, with unknown never meaning complete.
- `avendb/spec/AvenDB/PagedView.lean:15` explicitly does **not** prove that the dependency graph is complete for Lab reads or that a query's entry set is complete. Its page-closure and revision results cannot be relabeled as a query completeness proof.
- `avendb/spec/AvenDB/FileAvailability.lean:159` makes independently retained verified ranges the basis for byte completeness; a successful receive outcome alone is insufficient.

A safe first UI contract can say **local results**, distinguish loading/offline/refused/error/stale, and expose known pending dependencies. Calling a result **complete** requires a separately specified scope and exact revision plus authenticated evidence that all required index/entry/interpretation dependencies are covered. Do not infer that from `accepted`, zero announced missing logs, a successful bring, a warm view, or a displayed count. Existing `windowRead` callers that collapse a refusal/error to `null` (`src/lib/avendb/ops.js:144`) need a result-state adapter if the UI is to distinguish these cases truthfully.

## Cancellation and resource ownership

There are several different cancellation contracts today; they should not be conflated:

1. Read windows abort their current UI token and release scheduling demand. Session `near` checks device/route/signal before publishing or beginning later bring work (`session.svelte.js:638`).
2. `bringEntries` checks cancellation before and between its 64-entry batches (`game/code/sources/device.js:274`); an already issued `run(bring)` is still running.
3. Whole-file reads check an AbortSignal before and after each 4 MiB read, so cancellation prevents subsequent chunks (`src/lib/avendb/files.js:82`). `api.readFile` at `session.svelte.js:894` carries no signal into the worker/native operation. Stopping the service-worker bridge at `files.js:156` removes its listener but does not cancel an in-flight request already being answered.
4. `game/code/sources/device.js:350` allocates the whole requested file and uses a timeout; timeout does not cancel the underlying read loop. Shared asset/source promises are coalesced, but are not per-view ownership leases.

An end-to-end read-cancellation extension must identify the read owner/request across page, worker, Rust and native protocol paths. Cancel only that owner's unfinished read; retain shared readers and independently verified partial blocks. Never reuse this mechanism to abandon admitted writes or the durable shutdown fence. Coordinate with the file-availability and native lifecycle tasks rather than replacing their contracts.

## Prioritized implementation handoff

### Slice A: close concrete mounted-view gaps

Use the existing helpers first: bootstrap explicit unknown Note/Docs targets, add a retained Chat selected-room window, and bound visible room-head reads. Then connect entry windows for currently visible world-derived lists. Keep one scope per mounted owner with revision replacement; no scope-per-reactive-read allocation.

Acceptance: missing local target can request its known ID; explicit selection never silently changes to a different local record; late response after navigation/device change is ignored; old device receives its own release; overlapping owners survive one owner's close; pagination replaces stale demand; 150 rapid reactive reads reuse one scope and do not exhaust 128 tombstones. Offline/refused/empty states remain distinct. These plumbing changes must preserve existing authorization and mutation behavior.

### Slice B: make route context and leases match the UI

Define a bounded semantic context containing pathname, view identity, selected vault and query/page identity where relevant. Keep selected-entry/viewport scopes independent from the route bootstrap scope. Replan on meaningful changes and order selected/visible dependencies ahead of speculative learned entries. Specify background/pagehide expiry and foreground renewal. Distinguish unsupported `demand` from capacity refusal, with bounded retry.

Acceptance: Shell hash/vault switches replace the correct route demand, old owners cannot revive after release, rapid changes stay bounded, locked/replaced devices republish only current demand, and background tab suspension cannot hold an indefinite lease. A Lean model/proof is required before changing scheduler/revision rules: stale revisions cannot revive scopes, release preserves other owners, expiry bounds abandoned work, demand cannot enlarge authority. Follow with Rust/JS differential or protocol tests mapping to those rules.

### Slice C: typed dependency reporting

Specify the read dependency envelope before implementing a generic recursive collector. Include query/followed entry IDs, relevant schema/lens/cap-group/index dependencies, and file roots/ranges where the view actually requests bytes. Bound fan-out, recursion and memory; bind it to the read's exact revision/context. Keep manifest reference traversal a scheduling hint, not evidence of authority or dependency completeness.

Acceptance: nested follow/cycle/missing target cases; schema/lens/group replacement; revocation between result and follow-up; cross-vault references; depth truncation; stale index/revision rejection; deduplicated shared dependencies. Compare authorized output with the existing full read path. A complete dependency graph claim needs a matching Lean model and implementation mapping first.

### Slice D: truthful local results, then authenticated completeness

Add a uniform local-result state without pretending to know remote completeness. Design the later completeness protocol explicitly: who attests to which authorized matching set, against which revision, and what invalidates that attestation. Demand, peer log progress, and page availability remain separate dimensions. Treat empty results and pagination as first-class proof cases.

Acceptance: local empty while an allowed remote match exists never displays a global no-results verdict; unknown/offline peer coverage stays unknown; revoked/moved entries invalidate the correct result; page boundaries and counts bind to one revision; schema changes cannot preserve stale complete status. Reuse existing proofs only within their stated boundaries.

### Slice E: subscriptions, file ranges and large consumers

After the context/dependency contract is settled, connect query-specific invalidation/materialization instead of whole-world refresh (coordinate task 19). Extend file cancellation with shared ownership; represent Studio's visible clips/playhead-ahead ranges and asset scene dependencies (coordinate file/task 4 and later platform acceptance). Do not substitute query pagination for a bound on full local scans/materialization.

Acceptance: unrelated edits do not rebuild every view; relevant policy/schema/index changes still invalidate it; memory and queued work are bounded under scroll/navigation; abort stops new byte requests and eventually releases the active read, while another owner continues; verified partial data survives failover. Validate on actual iPad/WebKit hidden/resume and memory-pressure scenarios after deterministic tests pass.

## Existing verification to preserve

The repository already has focused tests in `game/code/sources/{demand,device,manifests}.test.js` and `src/lib/avendb/{query-window,visible-entries,preview-pool,preview-viewport,files}.test.js`. They cover scope coalescing/release/renewal, older API fallback, navigation and device replacement, explicit missing IDs, nonblocking local answers, independent windows, bounded previews, retry, stable viewport actions and stopping future file chunks. Rust demand tests cover revision/release/expiry/capacity and the scheduler has priority tests. Reuse these suites; do not replace them with tests that merely mirror new helper internals.

Still unverified by this audit: actual deployed manifests, account-specific viewport/dependency coverage, physical browser suspension behavior, dynamic sandbox/legacy adapter coverage, end-to-end active-read cancellation, and any authenticated query completeness guarantee. No latency, memory reduction or percentage-complete claim follows from this source inventory.
