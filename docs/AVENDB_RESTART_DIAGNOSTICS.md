## Actual reactive query emission timing

`query.first-nonempty-emission` starts when a new query subscription scope is created and ends after its first nonempty authorized result has been delivered to the consumer callback. Empty and refused replies do not finish the timer; subsequent revision reads share the initial clock. Replaced/closed subscriptions cannot publish or record stale answers. A callback that throws does not count as successful emission. This uses one local monotonic clock. `query.first-nonempty-emission.readonly` additionally identifies results containing read-only rows, without assuming their checkpoint origin. No IDs, query parameters or row contents enter the latency journal.

This measures request-to-reactive-consumer completion, **not** a rendered frame, whole-view readiness, complete discovery, file readiness, manifest-start latency or remotely observed write latency. The emitted result may still be partial. Empty-but-complete views are deliberately not counted as nonempty results. Remote write-to-render needs an authenticated observation acknowledgement from the actual subscribed UI with a nonce measured on the originating device; cross-device wall-clock subtraction is not valid evidence. That protocol is not introduced by this slice.

Validation: 18 reactive-read, reactive-latency and journal tests pass (60 assertions), including stale scope suppression, consumer failure and persistence privacy. The new standalone timing module passes checkJs. Checking the entire reactive-read dependency graph outside SvelteKit encounters the existing `$app/paths` alias, so integrated type checking remains with the coordinator.

## Remote reactive acknowledgement prerequisite

The existing peer receipt reports policy standing of an edit, not that a subscribed UI consumed it. Query rows previously supplied no frontier to identify the state the callback actually received. An explicit `observeRevision: true` query now adds bounded `observedRevision` metadata to already-authorized returned rows: `main-heads` or `checkpoint-basis`, at most 32 heads and a `frontierComplete` flag (only completeness of the returned frontier). Capture shares the same Lab read as the row. Normal queries incur no extra history lookup. A checkpoint basis remains owner-attested partial state, never a claim that a new edit was observed. `api.observe` accepts an optional fourth callback, invoked after successful consumer delivery, only for an opted-in query; it receives at most 64 projected metadata rows, no content. This metadata is ephemeral and is not added to persisted diagnostics.

Still required for genuine write-to-remote-reactive timing: an opt-in selected scope on both peers; a bounded pending nonce/edit tracker; actual receiver subscription metadata registered against that pending nonce; engine verification that the consumed frontier contains the target edit (not merely that current policy knows it); current disclosure/access checks before each request and acknowledgement; expiry and disconnect/cancellation cleanup; sender monotonic elapsed duration on the authenticated matching acknowledgement. Paint requires a separate renderer boundary. No existing policy observation is relabeled as UI visibility, and no cross-device timestamp subtraction is used.

Lean opt-in/authorization/bound contract passes. Twelve JS regressions (34 assertions) pass, including consumer-before-observation and diagnostic exceptions not breaking UI delivery. The focused Rust regression `query_observed_revision_is_opt_in_and_matches_the_authorized_get_frontier` is added but not executed on this lane to respect the coordinator's compiler queue. It must pass integrated validation before delivery. This is prerequisite plumbing, not completion of end-to-end remote visibility measurement.
